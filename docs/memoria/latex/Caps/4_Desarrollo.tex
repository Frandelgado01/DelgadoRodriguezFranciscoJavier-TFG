\subsection{Arquitectura}\label{subsec:Arquitectura}

El Cuaderno de Campo es una aplicación cliente-servidor en tres capas (figura~\ref{fig:Arquitectura}). El agricultor usa una aplicación web progresiva (PWA) que guarda los registros en el propio dispositivo cuando no hay cobertura; una API REST valida los datos y aplica las reglas de negocio; y una base de datos PostgreSQL los conserva. La misma base de datos almacenará los vectores del RAG mediante la extensión pgvector, de modo que no hace falta un segundo sistema. La elección de cada tecnología se justifica en el apartado~\ref{sec:Tecnologias}.

El despliegue es local, con Docker Compose, por acuerdo con el tutor. El servicio \texttt{web} (Caddy) sirve la PWA y hace de proxy de la API, de modo que ambas comparten origen; además, proporciona HTTPS con una autoridad de certificación propia \citep{caddy-https}, necesaria porque los \emph{service workers} solo funcionan en un contexto seguro \citep{mdn-service-worker}. El servicio \texttt{mailpit} recoge los correos sin enviarlos, lo que permite probar la recuperación de contraseña sin cuentas externas.

Tres episodios ilustran el papel de cada parte:

\begin{itemize}
	\item \textbf{El alumno se aparta de la recomendación de la IA.} Al clarificar el canal de los avisos de plazo, el agente recomendaba mostrarlos solo dentro de la aplicación. El alumno decidió enviarlos también por correo electrónico, porque el servidor ya necesitaba enviar correos para recuperar la contraseña y el coste añadido era bajo.
	\item \textbf{Un error del proceso detectado tarde.} La especificación se aprobó antes de contrastarla literalmente con el Boletín Oficial del Estado (BOE). El contraste, hecho después, encontró tres diferencias: los tres años de conservación cuentan desde la emisión del registro y no desde el tratamiento; la parcela se identifica por un número de orden correlativo; y la norma emplea el término <<aprovechamiento>>. Se corrigieron y se añadió al proceso la regla de contrastar antes de aprobar.
	\item \textbf{Un cambio de requisito empieza en la especificación.} Los perfiles de usuario y el guion de preguntas recogían los datos del Reglamento de Ejecución (UE) 2023/564, que la especificación no contemplaba. El alumno lo consultó y el tutor propuso incorporar solo la dosis por hectárea, calculada como la cantidad de cada producto entre la superficie tratada total. El cambio se hizo primero en la especificación (REQ-23), tras contrastar el reglamento con su publicación oficial, y después en el plan (\texttt{d5dd41d}) y en las tareas (\texttt{fa55163}), con la aprobación del alumno en cada paso. Las pruebas y el código corresponden al hito H4. \pendiente{actualizar al cerrar H4}
\end{itemize}

\section{Fase de generación con Claude Code en VS Code}\label{sec:Generacion}

\subsection{Preparación}\label{subsec:Preparacion}

El repositorio se preparó con Spec Kit (\texttt{specify-cli} 1.2.0), que instala las fases como \emph{skills} de Claude Code, y con un fichero \texttt{CLAUDE.md} que recoge el contexto, las reglas del registro, la trazabilidad y el formato de la memoria. Se configuró un único \emph{hook}, que recuerda al agente en cada petición la obligación de mantener el registro. No se han configurado \emph{hooks} que lancen pruebas tras cada edición: la verificación recae en la ejecución de las pruebas dentro de cada tarea y en el pipeline.

\subsection{Plan}\label{subsec:Plan001}

El plan de la 001 respondió a nueve preguntas preparadas de antemano sobre estructura, funcionamiento sin conexión, idempotencia, conflictos, modelo de datos, contrato, validaciones, sesión y avisos. Sus decisiones, numeradas de R1 a R15, recogen el motivo, las alternativas y las fuentes. Las más relevantes son las siguientes:

\begin{itemize}
	\item \textbf{Funcionamiento sin conexión (R3).} Los datos y una cola de operaciones se guardan en IndexedDB, y la cola se vacía al abrir la aplicación, al recuperar la red y de forma periódica. No se usa la API de sincronización en segundo plano porque Safari y Firefox no la implementan \citep{caniuse-background-sync}.
	\item \textbf{Idempotencia y conflictos (R4 y R5).} El cliente genera los identificadores, de modo que un reintento no duplica un registro. Si dos dispositivos modifican el mismo tratamiento, no se sobrescribe ninguna versión: ambas se conservan y el agricultor elige.
	\item \textbf{Reglas sin divergencias (R8).} La PWA valida sin conexión y la API vuelve a validar. Las reglas se implementan en las dos capas y se prueban con un mismo fichero de casos.
	\item \textbf{Sesión y contraseñas (R9).} Las contraseñas se protegen con Argon2id y la sesión usa un \emph{token} opaco del que la base de datos solo guarda su resumen criptográfico, siguiendo las guías de OWASP \citep{owasp-password-storage,owasp-session}.
	\item \textbf{Dosis por hectárea (R15).} No se almacena: se calcula a partir de la cantidad y las superficies, con aritmética exacta para que las dos capas redondeen igual.
\end{itemize}

El alumno revisó el plan y tomó cuatro decisiones: mantener la contraseña de 15 caracteres como mínimo, incorporar el límite de intentos, aceptar los umbrales de rendimiento y aplazar las diferencias con las variables del SIEX. Después fijó Chrome para Android como plataforma de referencia. El funcionamiento en iOS queda como compatible por diseño, pero no verificado.

\subsection{Tareas}\label{subsec:Tareas001}

La descomposición inicial produjo 70 tareas. El análisis de coherencia previo a la implementación encontró nueve hallazgos (cuatro altos, tres medios y dos bajos), que se corrigieron y añadieron una tarea; REQ-23 sumó otras seis, hasta un total de \textbf{77}. Ante la dificultad del alumno para seguir las 70 tareas iniciales, se buscó un seguimiento más manejable. La solución no fue agruparlas, porque se habría perdido la evidencia de que la prueba va primero, sino organizar la revisión en siete hitos con un criterio comprobable cada uno.
